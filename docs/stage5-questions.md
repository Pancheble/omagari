## 1. 물은 것

### Q1. 같은 사람의 작업끼리도 부딪힘을 보나

도그푸딩은 지금 일하는 모습 그대로다. 허브 세션 하나가 이슈마다 하위 세션을 띄우고, 하위 세션은 저마다 브랜치가 달라 작업이 여럿이다. 그런데 지금 러너의 직접 충돌 계산, 근처 작업, 세션 시작 훅은 로그인이 나와 같으면 건너뛰고, 기획 6장도 "한 사람의 에이전트끼리 부딪히는 것은 다루지 않는다"고 적었다. 4단계에서 #216과 #217이 둘 다 계약과 서버 파일을 고쳐 #216이 dev를 합치고 계약 버전을 다시 올려야 했는데, Omagari를 켜 두었어도 이 둘은 같은 사람의 작업이라 아무것도 나오지 않았을 것이다.

- A. 브랜치가 다르면 같은 사람이라도 남처럼 본다.
- B. 다른 사람끼리만 보고, 도그푸딩에 사람을 데려온다.
- C. A를 설정으로 두고 기본은 끈다.

고른 답: A. @Pancheble: "원래 그걸 노린거 아닌가? 한 사람이 여러 에이전트를 굴리는데 그 에이전트끼리 겹치잖아 … 나누는 기준이 사람이 아니라 에이전트임". 용어집에서 에이전트는 주인과 실행기 한 쌍이라, 나누는 기준은 작업(브랜치)으로 적는다.

### Q2. 5단계에 무엇을 넣고 어떤 순서로 하나

후보는 다섯이다: ① 배포(서버가 웹 화면도 내고, HTTPS 주소, DB 백업), ② 작업 단위 부딪힘(Q1), ③ 서버 하나에 워크스페이스 여럿과 워크스페이스 안의 레포 여럿, ④ 팀과 권한(작업, 보기), ⑤ 4단계에서 남은 것(Codex 작업 세션 포크를 러너에 붙이기, 375px 포럼 머리 띠 겹침). 외부 기여자의 기여 권한은 #211 순서대로 도그푸딩 뒤다. #167·#168은 업스트림을 기다려 넣지 않는다.

- A. ①②를 먼저 해 도그푸딩을 시작하고, ③④⑤는 도그푸딩하며 5단계 안에서 만든다.
- B. 5단계는 ①②⑤만. ③④는 도그푸딩에서 배운 것을 보고 6단계에서.
- C. ③④까지 다 만들고 배포한다.

고른 답: A. ③은 서버의 거의 모든 표에 레포를 더하는 넓은 고침이라 하위 세션 여럿이 같은 파일을 함께 고친다. Q1로 Omagari가 잡아야 할 바로 그 상황이라 도그푸딩 거리가 된다.

### Q3. 서버를 어디에 올리나

서버는 늘 켜져 있어야 하고(러너가 WebSocket으로 붙어 있다), SQLite 파일을 둘 지워지지 않는 디스크와 HTTPS 주소가 있어야 한다.

| | 한 달 | 좋은 점 | 걸리는 점 |
| --- | --- | --- | --- |
| A. Fly.io | 약 4~6달러(256~512MB, 디스크 10GB) | 디스크, WebSocket, `*.fly.dev` HTTPS, 날마다 디스크 스냅샷, GitHub Actions 배포 | Dockerfile이 필요하다 |
| B. VPS(Hetzner, AWS Lightsail) | 약 4.5유로, Lightsail 5달러 | 싸고 자유롭다 | HTTPS, 패치, 배포 스크립트를 직접 챙긴다 |
| C. 내 Mac과 Cloudflare Tunnel | 무료 | 바로 된다 | Mac이 잠들면 멈춘다. 하위 세션 테스트로 부하가 큰 기기다 |
| D. Railway | 5달러부터 | 화면에서 다 된다 | Hobby의 디스크가 출처마다 다르다 |

@Pancheble이 AWS를 물었다. AWS에서 맞는 것은 Lightsail(VPS라 B에 든다)뿐이다. App Runner는 요청과 응답에 맞춘 서비스라 WebSocket을 권하지 않고 지워지지 않는 디스크가 없다. Fargate는 WebSocket에 로드 밸런서(한 달 약 16달러)가 필요하고, 디스크가 네트워크 파일 시스템(EFS)이라 SQLite의 잠금이 깨질 수 있다.

고른 답: A(Fly.io). 1인 개발이라 서버를 관리하는 시간이 가장 비싸다. Fly 계정, 결제 카드, 배포 토큰을 GitHub 비밀값에 넣는 일은 @Pancheble이 한다.

### Q4. 배포 전에 보안 감사를 하나

@Pancheble이 [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill)(MIT)을 배포 전에 쓰자고 했다. 정찰, 갈래마다 따로 띄운 에이전트의 찾기, 찾지 않은 에이전트의 반박, 남은 것만 "확인됨"으로 적는 여섯 단계 감사이고, 보고서는 레포 밖에 쓰며 돌아가는 서버를 찌르지 않는다. 갈래 가운데 웹·인증(서버가 작업 중 코드와 토큰을 든다, ADR-0007·0025), AI·LLM(채널 글이 러너가 띄운 에이전트에 들어간다, 구현 11장), 로컬 IPC(훅과 러너의 유닉스 소켓), 테넌트 분리(워크스페이스 여럿)가 Omagari와 맞는다. Claude Code의 `/security-review`는 브랜치 diff만, gstack의 `/cso`는 반박 단계 없이 본다.

- A. 배포 전에 레포 전체를 감사하고 확인된 것을 고친 뒤 배포한다. 워크스페이스 여럿과 권한을 넣은 뒤 한 번 더 돌린다(지난 기록을 이어받아 빈 곳을 본다).
- B. 배포 전에 한 번만.

고른 답: A. 감사는 따로 띄운 세션에서 하고, 스킬은 레포 범위로 깐다. 이 레포는 공개라 재현 방법이 담긴 보고서는 레포 밖에만 두고 공개 이슈로 올리지 않는다.

### Q5. 도그푸딩 서버는 어느 판을 도나

ADR-0019는 서버와 멤버가 `main`을 쓰게 했고, `main`은 릴리즈 때만 나아간다(ADR-0022). 서버가 `main`을 따르면 허브가 `dev`에 머지한 것을 다음 릴리즈까지 도그푸딩에서 써 볼 수 없다.

- A. `dev`를 따른다. `dev`에 머지되고 CI가 통과하면 GitHub Actions가 Fly.io에 저절로 배포한다. @Pancheble의 러너도 `dev` 클론에서 돈다. `main`은 릴리즈한 판으로 남는다.
- B. `main`을 따르고, 써 보고 싶으면 릴리즈한다(ADR-0022와 부딪힌다).
- C. `dev`에서 배포하되 사람이 누를 때만.

고른 답: A. ADR-0042(Q3과 함께).

### Q6. 계약이 오른 판이 배포되면 러너는

지금은 계약이 다르면 서버가 러너를 받지 않고, 러너는 "받고 다시 켜세요"를 알리고 멈춘다. 그동안 하위 세션의 훅에는 "확인하지 못했다"만 들어간다. 러너 프로그램은 깔린 클론(README의 `~/omagari`)에서 돌고, 관측하는 것은 작업하는 레포 폴더다. 도그푸딩에서는 둘 다 omagari 레포지만 다른 클론이다.

- A. 러너가 스스로 받는다. 서버가 더 새로워 거절하면 깔린 클론에서 `git pull --ff-only`와 `npm ci`를 하고 다시 켠다. 고친 파일이 있거나 빨리 감기가 안 되면 알리기만 한다.
- B. 알리기만 하고, `omagari update` 명령 하나로 받기와 다시 켜기를 묶는다.
- C. 서버가 앞 판 몇 개의 계약을 받아 준다(Room, ADR-0019에서 버림).

고른 답: A. 받아 오는 코드는 GitHub의 우리 브랜치에서 오므로 손으로 받는 것보다 위험하지 않다. ADR-0042.

### Q7. 무엇을 레포마다, 무엇을 워크스페이스에 두나

러너는 레포 폴더 하나에 짝지어져, 채팅에서 `@호출`하면 어느 레포의 러너가 답할지 정해져 있어야 한다. 처음 안은 채널·포스트·라벨·결정을 레포마다, 포럼·멤버·팀을 워크스페이스에 두는 것이었다. @Pancheble: "레포랑 웍스페이스 둘다 둘 수 있게 하자 … 워크스페이스까지 올라가야하는 포스트가 뭐가 있지?", 이어서 "지금 말고 그냥 전체적인 프로젝트를 봤을때".

지금 포스트는 알림에서만 생기고 알림은 같은 레포의 두 작업 사이에서만 나므로, 워크스페이스 포스트가 생길 길이 없다. 프로젝트 전체로 보면 생길 곳은 두 갈래다.

- 알림에서: 레포를 넘는 계약 변경(`backend`가 응답 칸 이름을 바꾸는데 `web`과 `mobile`이 그 칸을 읽는다), 레포를 넘는 중복 구현, 레포를 넘는 간접 충돌. 직접 충돌은 같은 파일에서만 나 레포를 넘지 않는다.
- 사람이 여는 것: 여러 레포에 걸친 결정(구현 13장 미정), 아직 레포가 없는 주제(새 서비스를 뺄까), 워크스페이스 운영(팀 권한, 외부 기여자 규칙, 배포 일정).

걸리는 것은 논의 포스트가 그 레포의 GitHub 이슈이고 결정이 그 레포의 PR이라는 점이다. 알려진 답은 집 레포다. GitHub 조직 토론은 조직의 레포 하나를 원천으로 골라 그 레포에 담고 권한도 그 레포를 따른다. `rust-lang/rfcs`와 `kubernetes/enhancements`도 여러 레포에 걸친 제안을 전용 레포에 둔다.

- A. 5단계는 채널과 포럼만 두 층에 둔다. 포스트, 라벨, 결정, 작업은 레포마다다. 워크스페이스 포스트는 집 레포 방식으로 하기로 방향만 정하고, 레포 둘 이상으로 도그푸딩한 뒤 만든다.
- B. 집 레포와 사람이 여는 워크스페이스 포스트까지 5단계에 넣는다.
- C. 레포를 넘는 부딪힘 감지까지 넣는다.

고른 답: A. 그래서 이렇게 된다.

- 채팅 채널은 레포 밑에도 워크스페이스 밑에도 만든다. 레포 채널의 `@호출`은 그 레포의 러너가, 워크스페이스 채널의 `@호출`은 지금 규칙대로 그 멤버가 마지막에 붙인 러너가 답하고, 답에는 어느 레포와 브랜치를 보았는지 붙는다.
- 포럼의 거르기에 레포 조건이 더해진다. 레포 하나면 그 레포 밑에, 둘 이상이거나 모든 레포면 워크스페이스 밑에 보인다.
- 멤버, 프로필, 접속 상태, 상태 메시지, 팀은 워크스페이스에 하나다.
- 레포를 넘는 부딪힘은 6단계 후보의 맨 앞이다.

### Q8. 워크스페이스는 누가 만들고, 멤버와 팀은 어떻게 정하나

서버는 인터넷에 열려 있어 GitHub 계정만 있으면 누구나 로그인 화면까지 온다. 처음 안은 서버를 띄운 사람이 정한 계정만 워크스페이스를 만들고 push 권한자가 레포를 넣는 것이었다. @Pancheble: "깃허브 권한이랑 똑같이 ㄱㄱ". GitHub처럼 옮기면 누구나 만들고 소유자가 초대하며, 레포는 그 레포의 Admin이 넣고, 레포 안의 권한은 GitHub 권한을 그대로 읽는다(Write 이상은 작업, Read·Triage는 보기). GitHub이 돌려주는 레포 권한(`GET /repos/{owner}/{repo}`의 `permissions`)에는 팀으로 받은 몫이 이미 들어 있어, Omagari가 팀을 따로 가져올 필요도 `read:org`도 없다.

이어서 @Pancheble: "그냥 조직을 지금 만들고 지금처럼 운영하는게 좋을수도 있을거 같은데". 그러면 Omagari의 소유자, 초대, 팀이 모두 필요 없다. 사람과 팀은 GitHub이 맡고, Omagari는 지금처럼 push 권한으로 멤버를 정한다(ADR-0011). 마지막으로 @Pancheble: "개인 리포도 Omagari가 잘 작동하는지 확인은 해야해서 그냥 이대로 가자". 그래서 레포는 개인 계정에 그대로 두고 규칙만 이렇게 한다.

고른 답:

- 워크스페이스는 GitHub 계정(조직이나 개인) 하나와 짝짓는다. 만드는 화면도 Omagari의 소유자도 없다. 그 계정의 레포를 처음 넣으면 생긴다. 레포는 그 레포의 GitHub Admin이 넣고 뺀다. 한 레포는 워크스페이스 하나에만 들어가, 러너는 지금처럼 폴더의 원격으로 워크스페이스를 찾는다.
- 멤버는 워크스페이스 레포 가운데 하나라도 push 권한이 있는 사람이다. 초대 없이 로그인하면 들어온다. 레포마다 push 권한이 있으면 그 레포가 보이고, 작업 중 코드를 서로 본다. 10분마다 다시 확인한다(ADR-0011).
- 팀은 GitHub 팀이다. 팀에 Write를 주면 그 팀이 들어온다. Omagari는 팀을 만들지 않는다.
- 서버 설정에 받을 GitHub 계정 목록을 둔다. 도그푸딩 서버는 `Pancheble` 하나만 받는다(GitHub Enterprise Server의 "사용자가 조직을 만들 수 있음" 끄기와 같은 것).
- 보기(Read 권한만 있는 사람)와 기여(외부 기여자)는 도그푸딩 뒤다. 공개 레포의 Read 권한은 세상 모두라 오픈소스 문제와 함께 정한다.
- 조직 레포의 길(OAuth 앱 접근 제한 승인)은 조직 팀이 쓰겠다고 할 때 손 점검으로 본다.

ADR-0043.

## 3. 미정으로 남긴 것

- push 권한이 없는 사람의 자격: 보기(Read 권한만)와 기여(외부 기여자). 도그푸딩 뒤, 오픈소스 문제와 함께(구현 13장)
- 워크스페이스 포스트와 집 레포, 레포를 넘는 부딪힘(계약 변경, 중복 구현, 간접 충돌). 6단계 후보의 맨 앞
- 조직 레포의 길(OAuth 앱 접근 제한 승인). 조직 팀이 쓰겠다고 할 때 손 점검
- Fly 기계의 크기(256MB, 512MB). 써 보고 정한다
- #167·#168(sandbox-runtime 업스트림을 기다림)
