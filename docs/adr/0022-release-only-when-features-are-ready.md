# 릴리즈는 기능이 어느 정도 갖춰졌을 때만 한다

ADR-0019는 멤버나 서버가 받아야 할 feat나 fix가 `dev`에 쌓였을 때 릴리즈하게 했다. 그래서 1단계 동안 v0.1.0(2026-11-11)과 v0.2.0(2026-11-12)을 냈다. 하지만 Omagari는 지금 주인 혼자 만드는 1인 개발이라 릴리즈를 받아 쓸 멤버가 없다. 주인은 2026-11-12에 두 릴리즈를 지우고, "어느 정도 기능이 갖춰졌다 하면 그때 릴리즈 내는게 맞는거 같아"라고 정했다.

- **주인이 기능이 갖춰졌다고 할 때만 릴리즈한다.** 에이전트는 feat나 fix가 쌓였다는 이유로 릴리즈를 권하지 않는다. 주인이 릴리즈하라고 하면 ADR-0019의 절차대로 한다.
- **v0.1.0과 v0.2.0은 지웠다.** GitHub 릴리즈와 태그를 지웠다. `main`은 v0.2.0이었던 `ca15697`에 그대로 있다.
- **ADR-0019의 나머지는 그대로다.** 버전은 git 태그에서 읽고, `main`은 쓰는 판이며, 번호는 SemVer를 따른다. 계약이 바뀐 릴리즈의 노트에는 "러너도 업데이트해야 해요"를 적는다.

## Considered Options

- **ADR-0019대로 feat나 fix가 쌓일 때마다 릴리즈하기**: 받아 쓸 사람이 없어서 태그와 노트만 늘어난다.

## Consequences

- 다음 릴리즈 전까지는 태그가 없다. 그래서 체크아웃의 버전이 `버전 모름(커밋 abc1234)`으로 보인다(`checkoutVersion()`). 코드와 테스트는 이 경우를 이미 다룬다.
- 다음 릴리즈의 번호는 그때 정한다. 지운 번호를 다시 쓸 때, 그 태그를 이미 받은 클론은 새 태그를 받지 못한다. git은 같은 이름의 태그를 덮어쓰지 않기 때문이다([git-tag "On Re-tagging"](https://git-scm.com/docs/git-tag#_on_re_tagging)). 그런 클론은 `git fetch --prune --prune-tags`로 옛 태그를 지운다.
- 멤버가 생기면 ADR-0019의 기준(feat나 fix가 쌓였을 때)으로 돌아갈지 다시 정한다.
