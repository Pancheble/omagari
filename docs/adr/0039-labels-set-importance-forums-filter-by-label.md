# 라벨은 GitHub 라벨이고, 중요도는 라벨에 달고, 포럼은 라벨로 거른 보기다

ADR-0027은 알림 하나를 부딪힘 포럼의 포스트 하나로 올렸고, ADR-0032는 포스트마다 GitHub 이슈를 열었다. 3단계 화면 검수(#139)에서 @Pancheble이 "포럼에 그냥 대부분의 포스트가 다 올라가는거 같은데? 지저분하지 않아?"라고 했다. 기획 원칙 6과 구현 6장 표는 추정은 알리기만 하고 확인된 것만 소집하는데, ADR-0027은 그것과 견주지 않았다(#182). 4단계 그릴링에서 팀의 자유도를 열어 두는 쪽으로 정했다(2026-11-17 @Pancheble, `docs/stage4-questions.md` Q2~Q6, Q10).

- **라벨**: 레포의 GitHub 라벨 그 자체다(이름, 색, 설명). 종류 넷(직접 충돌, 간접 충돌, 중복 구현, 계약 변경)과 "확인됨"은 처음부터 있는 기본 라벨이다. 멤버 누구나 Omagari나 GitHub에서 라벨을 만들고 고친다.
- **붙는 길**: 알림을 올릴 때 종류 라벨과 경로 규칙의 라벨이 저절로 붙는다. 경로 규칙은 GitHub의 actions/labeler가 쓰는 `.github/labeler.yml`을 기본 브랜치에서 읽는다. 합쳐 돌려 보기가 깨지면 "확인됨"이 붙는다. 그 뒤엔 사람이 포스트나 이슈에서 붙이고 뗀다.
- **중요도**: 라벨마다 참고나 논의를 하나 단다. 팀에 하나라 모두에게 같고, 멤버 누구나 바꾼다. 기본은 확인됨과 계약 변경이 논의, 나머지와 새로 만든 라벨이 참고다. 포스트의 중요도는 그 라벨 중 가장 높은 것이다.
- **이슈**: 포스트의 중요도가 논의가 될 때 GitHub 이슈를 연다. 참고 포스트는 이슈가 없고 라벨은 Omagari에만 있다. ADR-0032의 "포스트 하나가 이슈 하나"를 "논의 포스트 하나가 이슈 하나"로 좁힌다.
- **포럼**: 중요도나 라벨(하나라도 맞으면)로 거른 보기다. 포스트는 포럼에 들어가 있지 않고, 맞는 포럼마다 보인다. 처음엔 "논의"(지금의 "부딪힘" 포럼)와 "참고"가 있고, 멤버 누구나 포럼을 만들고 고치고 지운다. 어느 포럼에도 맞지 않는 포스트는 "다른 포스트"에 보인다. 설정 창의 "알림을 올릴 포럼"은 없어진다.

## Considered Options

- **종류 단위로 받고 중요도는 고정**: 원칙 6을 설정으로 깨뜨릴 수 없다. @Pancheble이 팀의 자유도를 해친다고 했다.
- **경로 규칙만, 또는 사람이 단 라벨만**: 경로 규칙만이면 사람이 고칠 길이 없고, 사람만이면 처음엔 맞는 포럼에 오지 않고 참고 포스트에는 붙일 이슈도 없다.
- **멤버마다 다른 중요도**: 같은 포스트가 누구에겐 이슈이고 누구에겐 아니게 된다. 개인이 무엇을 볼지는 포럼을 고르는 것으로 된다.
- **포스트가 포럼 하나에만 속한다**: 라벨이 둘이면 어디에 둘지 우선순위를 또 정해야 한다. GitHub의 저장한 거르기처럼 겹쳐 보이게 했다.
- **Room**: 라벨이 없다. 메시지마다 급한 정도(fyi, notify, interrupt)를 코드가 정하고, 포럼과 포스트가 없다.

## Consequences

- 이슈를 연 뒤 중요도가 내려가도 이슈는 그대로 둔다. Omagari가 이슈를 닫는 것은 알림이 풀릴 때뿐이다(ADR-0032).
- 이미 쌓인 포스트에는 종류 라벨과 확인됨을 붙이고, 이미 열린 참고 포스트의 이슈는 닫지 않는다.
- 라벨의 이름, 색, 설명은 주기마다 GitHub에서 읽는다. 중요도는 GitHub 라벨에 칸이 없어 Omagari에 둔다.
- `labeler.yml`은 파일 조건(`changed-files`의 글롭)만 쓰고, 알림의 파일(직접 충돌은 부딪힌 파일, 나머지는 심볼이 있는 파일)에 맞춘다.
- 계약에 라벨, 중요도, 포럼의 거르기가 더해지고 `CONTRACT_VERSION`이 오른다.
- 편지함은 바뀌지 않는다. 중요도와 상관없이 두 작업의 편지함에 들어가고, 참고는 에이전트가 편지함으로 받아 처리한다.
