# 2단계 그릴링: 질문, 스스로 답한 것, 미정

범위는 구현 문서 1장의 2단계("흐름 하나")다: 직접 충돌·추정 알림 → 그 자리의 대화 → 결정 PR. 선점, 편지함과 피드, 묻고 기다리기(`omagari ask`), 정의 줄을 함께 넣고, 토론 엔진 없이 사람이 정리한다. 합쳐서 돌려 보기(3단계)와 토론(4단계)은 범위 밖이다.

찾아본 곳은 AGENTS.md 순서 그대로다: 기획·구현 문서, `GLOSSARY.md`, `docs/adr/`, `docs/stage1-questions.md` 4장(2단계를 열 때 물을 것), `docs/room-behavior.md`와 `../room-reference`(커밋 `917b8d4`), 지금 코드(러너의 근처 작업, 서버의 GitHub 연결).

## 1. 물을 것 (1라운드)

### Q1. 묻기(`omagari ask`)의 비용에 받는 쪽이 어떻게 동의하나

묻기는 상대의 에이전트를 상대의 사용량으로 부른다. "에이전트는 주인만 부를 수 있다"(구현 1장)와 어긋나 2단계에서 먼저 정하기로 했다(ADR-0009). Room에는 동의 장치가 없다. 받는 사람의 작업 세션이 편지함으로 받아 직접 답하고, 방에 들어온 것이 곧 동의다.

- A. **받는 쪽 스위치**: 멤버마다 "내 에이전트가 남의 질문에 답한다"를 켜고 끈다. 4단계의 자동 참여 스위치(구현 7장)를 이 스위치로 함께 쓴다. 받는 사람은 자기 에이전트가 무엇에 답했는지 본다.
- B. **묻는 쪽 비용**: 묻는 사람의 러너가 상대의 관측(바뀐 파일 내용)을 기준 커밋 위에 얹은 임시 트리에서 자기 실행기로 답한다. 동의가 필요 없다. 대신 상대가 full이 아니면 모르고, "상대 에이전트에게 묻는다"가 아니게 된다.
- C. **질문마다 승인**: 받는 사람이 웹에서 허락해야 러너가 돈다. 묻는 에이전트가 사람을 기다린다.

고를 답: A, 기본은 켜짐. 두세 명 팀에서 기본이 꺼짐이면 아무도 켜지 않아 묻기가 돌지 않는다. 받는 쪽 러너가 오프라인이면 질문을 남겨 두었다가 러너가 붙을 때 답하고(14일 뒤 만료, Room의 편지함), 묻는 쪽에는 바로 "오프라인이라 돌아오면 답한다"를 돌려준다.

### Q2. 알림은 어느 채널에 올라가나

기획 6장은 "Omagari의 알림은 한 줄 시스템 메시지로 올라온다"고만 적었다. Room은 채널이 없고 편지함으로만 보낸다.

- A. **알림 채널 하나**: 처음 알림을 올릴 때 서버가 "부딪힘" 채널을 만든다. 보통 채팅 채널이라 사람도 거기서 말한다.
- B. **고른 채널**: 워크스페이스 설정에서 고른다. 고르기 전에는 가장 먼저 만든 채널. 설정 화면이 하나 는다.

고를 답: A.

### Q3. 알림에서 시작하는 대화는 어떤 모양인가

기획 6장은 "그 메시지에서 바로 대화나 포스트를 시작한다", 7장은 "알림에 달린 토론 포스트"라고 적었다. 1단계는 포럼 채널과 포스트를 뺐다(PRD #3).

- A. **알림에 포스트가 달린다**: 알림에서 "이야기하기"를 누르면 그 알림에 달린 포스트가 열린다. 포스트 안에서 채널처럼 글을 쓰고 DM과 `@호출`을 쓴다. 결정은 포스트에서 정리한다. 4단계의 토론 포스트도 같은 자리에 붙는다. 포럼 채널은 2단계에도 만들지 않는다.
- B. **채널에서 이어 말한다**: 알림 아래에 그대로 이야기하고, 결정을 정리할 때 출처로 메시지 구간을 고른다.

고를 답: A. 알림 하나의 대화가 한곳에 모이고, 결정 PR의 출처가 포스트 링크 하나가 된다.

### Q4. 결정 PR은 누구 이름으로 여나

구현 2장은 "GitHub 앱"이 결정 PR을 만들고 머지한다고 적었다. 지금 서버는 로그인할 때 멤버마다 `repo` 범위 토큰을 받아 들고 있다.

- A. **정리한 멤버의 토큰**: 그 사람 이름으로 브랜치, 커밋, PR을 만든다. 새로 등록할 것이 없다.
- B. **GitHub 앱**: 앱을 새로 만들어 레포에 깔고, 서버가 앱 키를 든다. PR이 봇 이름으로 열린다.

고를 답: A. GitHub 앱은 Omagari를 쓰지 않는 팀원에게 GitHub로 알려야 할 때 만든다.

### Q5. 이의 창을 2단계에 넣나

구현 8장: 결정 PR이 열려 있는 동안이 이의 창이고, 이의가 없으면 Omagari가 머지한다. 되돌리기 어려운 것은 기본 하루, 쉬운 것은 바로 머지한다. 기본 길이는 13장의 미정이다.

- A. **넣는다**: 정리한 사람이 "바로"나 "하루"를 고른다(기본 하루). 창이 닫힐 때 이의가 없고 GitHub 규칙상 머지할 수 있으면 Omagari가 머지한다. 이의는 포스트의 "이의" 버튼이나 GitHub의 변경 요청 리뷰로 낸다. 이의가 나면 창이 멈추고 포스트로 돌아간다.
- B. **뺀다**: 사람이 GitHub에서 머지한다. Omagari는 PR 상태만 읽어 제안됨과 수락됨을 보인다.

고를 답: A. "관문 대신 이의 창"(원칙 4)이 결정 PR의 쓸모다.

### Q6. 다른 단계의 넘어가는 조건도 없애나

1단계의 "두세 명이 매일 들어온다"는 없앴다(ADR-0021). 남은 조건은 2→3 "알림에서 결정까지 이어진 사례가 나온다", 3→4 "자동 감지의 정밀도가 쓸 만하다", 4→이후 "알림만 보낼 때보다 결과가 낫다"다(구현 1장).

- A. **모두 없앤다**: 단계는 만드는 순서로만 남는다. 앞 단계를 다 만들면 다음 단계를 연다. 정밀도와 토론의 효과는 구현 12장의 지표로 재고, 토론이 효과가 없으면 남기지 않는다(기획 8장 리스크)는 그대로 둔다.
- B. **2단계부터는 남긴다**: 1단계만 사람 수라 뺐고, 나머지는 기능이 제 몫을 하는지를 본다. 남기면 2단계를 어떻게 셀지 다음 라운드에서 묻는다.

고를 답: A. 1단계 조건을 없앤 까닭("쓸 거리가 있어야 쓴다")이 2단계에도 똑같이 걸린다. 알림에서 결정까지의 사례도 3단계의 합쳐 돌려 보기가 있어야 더 자주 나온다.

### Q7. `omagari impact`와 밀어 넣기도 2단계에 넣나

구현 4장은 계약 선언, 응답에 끼워 넣기, `omagari impact`, 밀어 넣기, `omagari ask`를 2단계에 넣는다고 적었다. 밀어 넣기는 실행 중인 작업 세션에 급한 것을 바로 보내는 것이다. Room은 Claude Code의 세션 간 메시지(2.1.224+)와 Codex 앱 서버의 대기열을 쓴다. 우리 러너에서 되는지는 확인하지 않았다(1단계 질문 3장).

고를 답: `omagari impact`는 넣는다(심볼 색인 위의 조회 하나). 밀어 넣기는 빼고 미정으로 남긴다. 급한 것도 다음 훅이나 CLI 응답에 실린다.

### Q8. 웹에 선점과 편지함을 보이나

고를 답: 보이지 않는다. 선점과 편지함은 에이전트가 쓰는 것이라 CLI와 훅으로만 오간다. 2단계에서 웹에 새로 그리는 것은 알림 한 줄, 포스트, 결정 정리와 결정 PR 상태, 묻기 스위치(Q1이 A면), 직접 충돌이 걸린 작업의 표시(구현 6장 "상태 한 줄에 표시")다.

### Q9. 결정함과 결정 보기를 2단계에 넣나

PRD #3은 둘을 2단계로 미뤘지만, 단계 표의 2단계 줄에는 없다.

고를 답: 빼고 이후로 미룬다. 결정 PR이 열리고, 이의가 나고, 머지되면 그 포스트와 알림 채널에 한 줄씩 올라간다. 두세 명이면 이것으로 이의 창을 놓치지 않는다.

### Q10. 지표(`omagari metrics`)는 어떻게 하나

ADR-0018로 날마다 들어온 멤버 수와 문답 수를 센다. 1단계의 넘어가는 조건을 재려고 만들었는데, 그 조건이 없어졌다.

- A. **그대로 둔다**: 이미 있고 싸다. 2단계에서 더하지도 지우지도 않는다.
- B. **지운다**: ADR-0018을 대체하고 들어온 멤버 기록(`visits`)과 명령을 뺀다.
- C. **2단계 흐름의 수를 더한다**: 알림 수, 대화가 시작된 알림 수, 결정 PR 수(Q6이 B면 이것으로 잰다).

고를 답: A. Q6이 B면 C를 더한다.

## 3. 미정으로 남긴 것
