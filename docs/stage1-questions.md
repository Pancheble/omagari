# 1단계 그릴링: 질문, 스스로 답한 것, 미정

범위는 구현 문서 1장의 1단계(러너 → 서버 중계 → 관측 → 웹 화면)다. 찾아본 곳은 AGENTS.md 순서 그대로다: 두 문서, `../room-reference`(동작은 `docs/room-behavior.md`), 공식 문서. 용어는 `GLOSSARY.md`, Room과 다른 점은 `docs/adr/`에 있다.

## 1. 결정이 필요한 질문 (1라운드)

각 질문에 "예"라고 답하면 내가 고른 답을 받아들이는 것이다.

**Q1. 선점, 편지함, 묻고 기다리기를 2단계로 미룰까?**
1장의 1단계 목록에는 러너, 채널, 사람 옆의 에이전트, 상태 한 줄, DM과 @호출, 두 훅만 있고, 이 셋은 없다. 1단계에는 편지함에 넣을 알림(부딪힘)이 아직 없다. `omagari ask`는 상대의 러너가 상대의 사용량으로 답하는데, 1장은 "에이전트는 주인만 부를 수 있다"고 적었다. 이 둘이 어긋난다.
➡️ 예. 1단계의 두 훅은 관측과 상태 한 줄로 근처 작업만 보여 준다. 셋은 2단계의 부딪힘 알림과 함께 넣고, 그때 ask의 비용을 받는 쪽이 동의하는 방식(토론의 자동 참여 스위치와 같은 스위치)을 정한다.

**Q2. 1단계 관측은 바뀐 파일과 그 내용까지 올리고, 정의 줄은 2단계로 미룰까?**
관측이 내용을 올리는 것은 정해졌다(ADR-0007). 남은 것은 순서다. 내용 올리기는 파일을 읽고 빼는 규칙을 거는 일이라 불확실한 것이 적다. 정의 줄은 간접 충돌(2단계)에서 쓰이고, 언어마다 파서를 붙여야 해서 1단계의 불확실성을 늘린다.
➡️ 예. 1단계 관측은 작업마다 바뀐 파일과 그 내용을 공유 수준대로 올린다. 정의 줄은 2단계에서 넣는다.

**Q3. 상태 한 줄의 수명을 이렇게 정할까?** (구현 13장 미정 "언제 갱신할지")
Room에는 상태를 쓰는 도구가 따로 없고 선점·기다리기·끝내기가 상태를 덮어쓴다. 우리는 에이전트가 직접 쓰므로, 끝난 뒤에도 "~하는 중"이 남는 문제가 생긴다.
➡️ 예.
- 에이전트는 작업을 시작할 때, 방향이 바뀔 때, 끝낼 때 쓴다. 끝낼 때는 "끝: <요약>"으로 쓴다.
- 보이는 줄은 이 순서로 고른다: 오프라인 → 에이전트가 쓴 줄 → 초안 PR 제목 → 고치는 파일("payment.ts 외 3개 수정 중") → 바뀐 것이 없으면 줄 없음.
- 에이전트가 쓴 줄 옆에는 쓴 시각("2시간 전")을 붙인다.
- 그 브랜치가 머지되거나, 관측된 변경이 0이 되면 쓴 줄을 지운다.

**Q4. 채널 대화는 DM 세션에 "지난 턴 이후의 것만" 넘길까?** (구현 13장 미정)
채널 세션은 이어 가는 세션이라 앞에서 넘긴 대화는 이미 기록에 있다.
➡️ 예. 매 턴에 지난 턴 이후의 채널 메시지만 데이터로 감싸 넘긴다. 첫 턴은 최근 50개까지. 작업 세션의 맥락은 1단계에서 넣지 않는다(실행 중인 세션 포크가 미정이라).

**Q5. 워크스페이스에는 레포 push 권한이 있는 GitHub 계정만 들어오게 할까?**
관측이 작업 중인 파일 내용을 서버에 올리므로(ADR-0007), 워크스페이스에 들어온 사람은 그 코드를 본다. Room은 같은 이유로 push 권한을 요구한다.
➡️ 예. 따로 초대 화면을 만들지 않고, GitHub 로그인 때 그 레포의 push 권한으로 정한다.

**Q6. 1단계 서버는 우리가 띄우는 서버 하나로 할까?** (구현 13장 미정)
➡️ 예. 1단계는 두세 명이 쓰는 서버 하나에 워크스페이스 하나다. 팀마다 직접 띄우는 묶음(Room은 이것만 있다)은 다른 팀이 쓰겠다고 할 때 만든다.

**Q7. "상황 보기"와 "상태 한 줄 쓰기"를 다른 명령으로 나눌까?**
구현 4장은 `omagari status`를 상황 보기로, 5장은 `omagari status "..."`를 상태 한 줄 쓰기로 적었다. 읽기와 쓰기가 인자 하나로 갈린다.
➡️ 예. 읽기는 `omagari status`, 쓰기는 `omagari status set "<한 줄>"`.

## 3. 미정으로 남긴 것

문서로 확인하지 못해 추측하지 않았다. 만들면서 확인한다.

- 주인이 지금 쓰고 있는 세션을 포크하면 어디까지의 대화가 들어오는가 (구현 1장)
- 화면 없이 띄운 채널 세션이 길어지면 자동 컴팩트가 일어나는가, 일어나면 무엇이 남는가
- Codex에 `codex exec`용 포크가 있는가 (A2: 문서에 없음)
- 서버에서 받은 푸시 전 코드를 러너에서 합쳐 돌릴 때의 안전장치. 서버가 뚫리면 테스트 실행이 임의 코드 실행이 된다(3단계, 구현 13장)
- 실행 중인 작업 세션에 밀어 넣기. Room은 Claude Code 세션 간 메시지(2.1.224+)와 Codex 앱 서버 대기열을 쓴다. 우리 러너에서 같은 길이 되는지는 확인하지 않았다(2단계)

## 4. 다음 라운드 (Q1의 답에 따라)

Q1에 "예"면 2단계를 열 때 묻는다. "아니오"면 이것들이 1단계의 다음 라운드가 된다.

- 편지함의 주인은 사람인가 작업인가. 고를 답: 작업. 사람 앞으로 온 것은 그 사람의 모든 작업에 넣는다
- 편지함 전달 보장. 고를 답: Room처럼 넘겨준 것이 확인될 때까지 남기고(중복은 되고 유실은 안 됨), 14일 뒤 만료
- `omagari ask`에 답하는 러너 세션은 무엇을 보나. 고를 답: 포크가 확인되기 전에는 상대의 상태 한 줄, 브랜치 diff, 초안 PR
- ask는 바로 돌아오고 답은 편지함으로 오나. 고를 답: 예, 그리고 `omagari wait`로 최대 100초까지 기다린다(Room과 같음). 시간이 다 되어도 답으로 치지 않는다
- 선점은 언제 끝나나. 고를 답: `omagari release`, 브랜치가 머지되거나 지워질 때 자동, 오프라인 7일 뒤 삭제
- 편집 전 훅이 "선점하라", "묻거나 기다려라"처럼 행동을 권할까. Room은 권한다. 고를 답: 권하되 막지는 않는다
- 계획을 못 이룬 채 선점을 풀면, 그 계획을 본 사람에게 "취소됨"을 보낼까. Room은 보낸다. 고를 답: 예
